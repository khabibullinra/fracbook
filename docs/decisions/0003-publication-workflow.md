# ADR-0003: Автопубликация через CI + ветка `dev` + форки для студентов

## Статус

Принято, июль 2026. Заменяет ручную публикацию через `tools/publish_pages.py`
(см. ADR-0001, секция «Решение»).

## Контекст

По состоянию на ADR-0001 публикация сайта на GitVerse Pages работала так:

- Локально: `pytest -q` + `ruff check src tests` + `quarto render book/`
- Локальный скрипт `tools/publish_pages.py` (кросс-платформенный драйвер +
  шимы `.sh`/`.cmd`/`.ps1`) коммитил `book/_book/` в worktree `.worktrees/pages`
  и пушил в `origin/pages` через `force-with-lease`.
- CI делал только smoke-test (`pytest` + `ruff`) и грузил `_book/` как артефакт.

За полгода эксплуатации выявлены неудобства:

- **Дублирование.** CI и локальный скрипт делают одно и то же (тесты + render +
  копирование в `pages`). Логика публикации живёт в двух местах.
- **Зависимость от Positron.** На Windows у преподавателя Quarto встроен в
  Positron; без него публикация не работает. Публикация требует ручного
  запуска скрипта + наличия SSH-ключа к GitVerse.
- **Единственная стабильная ветка (`master`).** PR студентов шли напрямую в
  `master`; пока PR открыт, в `master` нет ничего, или есть недоделанный код.
  Между «всё горит зелёным» и «преподаватель вручную публикует» — зазор, в
  котором состояние master «неопределённое».
- **Студенты пишут в основном репо.** Каждому выдавалась роль Developer, что
  давало прямой push в основной репо. Случайный `git push --force` от студента
  мог сломать чужие ветки.

## Решение

Переход на «CI публикует, преподаватель только ревьюит».

### Ветки

```
feature/*, student/<ник>/* ──PR (review)──> dev
                                            (CI: smoke)
                                              │
                                              ▼ (PR от преподавателя, релиз)
                                            master (CI: smoke + render + auto-publish pages)
                                              │
                                              ▼
                                            pages
```

- **`dev`** — основная ветка разработки. Сюда идут PR студентов и преподавателей.
  Защищена branch protection (require PR + review + CI green).
- **`master`** — стабильная. Сюда попадает только то, что прошло ревью в `dev`.
  Защищена branch protection (require PR от преподавателя + review + CI green).
  Push в `master` триггерит автопубликацию в `pages`.
- **`pages`** — артефактная ветка для GitVerse Pages. Создаётся и поддерживается
  только CI. Любой ручной push в `pages` запрещён (на уровне GitVerse).

### Студенческий workflow

Студенты работают **через форк** (см. `docs/student-workflow.md`):

1. Форк `khabibullinra/fracbook` в свой аккаунт GitVerse.
2. `git clone` своего форка.
3. Ветка `student/<ник>/<короткое-описание>`.
4. Работа, коммиты, push **в свой форк**.
5. PR из своего форка в `khabibullinra/fracbook:dev`.

Преимущества: безопасность основного репо по построению, стандарт open source,
навык переносится на любой проект. Сложность для новичка снимается подробной
инструкцией в `docs/student-workflow.md` и вводным семинаром по Git.

### CI (`.gitverse/workflows/ci.yaml`)

Два job-а:

- **`test`** — на каждый push и PR в `dev` и `master`. Прогоняет `pytest`,
  `ruff check src tests`, `quarto render book/`. Загружает `book/_book/` как
  артефакт `book-html` (хранится 7 дней). Без `quarto render` для PR в `dev` —
  только `pytest` + `ruff` (быстрее; полный render — на push в `master`).
- **`publish`** — только на push в `master`, после зелёного `test`. Клонирует
  ветку `pages` через `actions/checkout` с токеном `${{ secrets.PAGES_TOKEN }}`,
  копирует `book/_book/` + `tools/404.html`, коммитит `publish: YYYY-MM-DD`,
  пушит `force-with-lease`.

### Безопасность

- **`secrets.PAGES_TOKEN`** — bot-токен GitVerse с правом push в `pages` и
  только в `pages`. Хранится в Secrets репо, в `ci.yaml` доступен только в
  job-е `publish` (на master).
- **Branch protection** настраивается в UI GitVerse:
  - `master`: require PR + ≥1 review + `test` job зелёный. Прямой push запрещён.
  - `dev`: require PR + ≥1 review + `test` job зелёный. Прямой push запрещён.
- **PR из форка** в `dev` — единственный путь для студента попасть в основной
  репо. Без fork-роли в GitVerse, без риска прямого push.

### Что удаляется

- `tools/publish_pages.py` — логика переехала в CI.
- `tools/publish-pages.sh`/`.cmd`/`.ps1` — шимы, ставшие ненужными.

## Последствия

### Плюсы

- **Минимум ручных действий.** `git push origin master` через ~2 мин → сайт
  обновлён. Не нужен ни скрипт, ни SSH-ключ, ни локальный Quarto (для
  публикации).
- **Единый источник истины для CI и прода.** То, что в CI зелёное, ровно то
  попадает на сайт. Локальный рендер преподавателя — для разработки, не для
  публикации.
- **dev как буфер.** PR студентов могут ломать `dev` — `master` не пострадает,
  сайт лежать не будет.
- **Студенческий навык.** Форки — стандарт open source; этот опыт переносится
  на любой проект.
- **Не зависим от Positron.** Quarto CLI ставится в систему отдельно, без
  привязки к IDE.

### Минусы

- **Доверие к CI-токену.** Если `PAGES_TOKEN` утечёт, можно запушить в
  `pages`. Митигация: токен создаётся с минимальными правами (только push
  в `pages`, ничего больше); ротация при подозрении на компрометацию.
- **Двухступенчатый workflow.** PR → dev, потом PR → master. Небольшой
  оверхед для преподавателя (раз в неделю).
- **Зависимость от CI.** Если CI ляжет, новые изменения в `pages` не
  попадут. Митигация: `quarto render` + push в `pages` можно сделать
  локально вручную, если скрипт восстановить (но в репо его больше нет —
  см. ниже).
- **Локальный Quarto обязателен для разработки.** Если раньше преподаватель
  мог публиковать без локального Quarto (через Positron), теперь для
  разработки (рендер перед PR) Quarto нужен в системе.

### Откат

Если автопубликация через CI сломается (например, утечка токена, изменение
API GitVerse):

1. Отключить триггер `publish` в `ci.yaml` (`if: false`).
2. При необходимости — вернуть `tools/publish_pages.py` из git-истории
   (`git revert <commit-удаливший-скрипт>` или `git show <commit>^:tools/publish_pages.py > tools/publish_pages.py`).
3. Публиковать вручную.

## Альтернативы, которые отклонили

- **Только `master` без `dev` (без двухуровневой модели).** Без `dev` любая
  поломка в PR студента сразу лежит в `master` → лежит сайт. Буфер нужен.
- **Approval gate в CI** (как GitHub environments с required reviewer).
  GitVerse environments на момент принятия решения не поддерживает required
  reviewers для workflow; ручной gate через UI не получился бы без
  отдельного клика. Решили: доверие к branch protection + ревью перед
  мержем в `master` достаточно.
- **Публикация по тегу (`v1.2.3`).** Безопаснее, но замедляет публикацию
  мелких правок. Студенческий PR про опечатку должен ждать тег — неудобно.
- **Прямой доступ (роль Developer) для студентов.** Проще для совсем
  начинающих, но любой `--force` от студента потенциально ломает основной
  репо. Форк архитектурно исключает эту проблему.
- **Jupyter Book / MkDocs / Sphinx.** См. ADR-0001 — Quarto остаётся.
